## 0. The one architectural rule everything below follows

> MCP Client -> **MCP Server (new)** -> existing `GraceAiToolsRegistry` + `SecureAiToolExecutor` -> existing RBAC/tenant-isolation checks -> existing domain services / Postgres RPCs -> Supabase Postgres

The MCP server is a **protocol adapter**, not a second authority. It must never re-implement authentication, RBAC, tenant scoping, Zod validation, or audit logging — all of that already exists in `src/lib/ai/secure-tool-executor.ts` (audit S7.3) and must be called into, not duplicated. Where a requested MCP tool doesn't yet exist internally, this document says so explicitly instead of inventing a shortcut.

### 1.2 Recommendation: **Supabase Edge Functions**

The hypothesis in the request is correct, but only after validating it against the two rows that actually decide it here: **existing precedent for JWT-based identity re-derivation** (the exact pattern `SecureAiToolExecutor` already requires) and **not adding a second vendor surface** for a backend that is already fully committed to Supabase. Every other row is neutral-to-favorable for Supabase and never favors Vercel outright. Concretely: create the MCP server as a new function under `supabase/functions/` (proposed name: `mcp-financial`), following the same shared-helper pattern already established by `_shared/`.

### 1.3 Should A2A orchestration (when it eventually exists) share this runtime?

**No — recommend separate deployables even though both would live on Supabase.** This is a forward-looking note only; no A2A design is being produced in this pass. Reasoning, given the original brief's own A2A requirement that "all agents must remain independently deployable and replaceable with no hard dependencies between agent services":

- The MCP server is stateless, short-lived, read-only request/response — a clean fit for one Edge Function.
- A future Finance/Auditor/Report agent pipeline is fundamentally different in shape: multi-step, potentially slower (chained LLM calls), and by the brief's own requirement must be independently deployable/replaceable. Bundling agents into the MCP function would violate that requirement immediately.
- Recommendation for whenever that phase is approved: each agent is its **own** Edge Function (or its own service, if scaling ever demands more than Edge Functions can give), communicating via A2A task/message format, but **every** agent still calls through the same `SecureAiToolExecutor` boundary — shared security authority, independent deployability. This mirrors the precedent already in this repo: Hermes (a separately deployable Telegram bridge) talks to Grace Ledger only through that same executor (audit S7.5).

### 1.4 Conditions that would change this recommendation

- If a future RAG ingestion job needs sustained processing time far beyond Edge Function execution limits (e.g., re-embedding a large historical document set in one run), that **specific batch job** — not the MCP server — might warrant a separate long-running worker (e.g., a queue-triggered process outside Edge Functions). This would not change where MCP itself lives.
- If the MCP TypeScript SDK proves incompatible with the Deno edge runtime (see Risk 1, S13) and a hand-rolled protocol implementation is rejected, that could force a Node-based runtime (Vercel or otherwise) purely for SDK compatibility — a technical constraint, not an architectural preference.

## 2. MCP transport design

**Transport:** MCP "Streamable HTTP" (the current spec's remote-server transport — a single HTTP endpoint handling JSON-RPC POST requests, with optional SSE upgrade for server-to-client streaming), not stdio (stdio is for local-process MCP servers, not applicable to a hosted Edge Function).

- **Endpoint:** one route, e.g. `POST https://<project>.supabase.co/functions/v1/mcp-financial`. Handles the three MCP methods this server needs: `initialize`, `tools/list`, `tools/call`. No other MCP capabilities (resources, prompts, sampling) are in scope for a read-only financial-data server.
- **Authentication:** Supabase's platform-level JWT verification (`verify_jwt` default-on, confirmed in `config.toml`) gates the endpoint before the function body runs at all — a request with no valid Supabase-issued JWT never reaches application code. Inside the function, construct a `SupabaseClient` using the forwarded `Authorization` header (mirrors what `SecureAiToolExecutor` already assumes) and call `supabase.auth.getUser()` to get a trusted identity — never trust an identity claim inside the MCP request body.
- **Session handling:** MCP's Streamable HTTP transport supports an `Mcp-Session-Id` response header after `initialize`, expected on subsequent requests. Recommend treating this as a **correlation id only, not an authorization mechanism** — Edge Functions are stateless/ephemeral (no shared in-memory session store survives across invocations or scale-out instances), and every `tools/call` re-authenticates via the JWT and re-derives `church_id`/role from `profiles` regardless of session id, exactly as `SecureAiToolExecutor` does today. This avoids building fragile in-memory session state that wouldn't survive a cold start.
- **Request validation:** the MCP JSON-RPC envelope (`jsonrpc`, `id`, `method`, `params`) is validated with its own Zod schema before dispatch; tool-specific parameters are then validated again by the tool's own input schema inside `SecureAiToolExecutor` (no change there — this is a second, outer validation layer, not a replacement).
- **CORS:** default-deny. MCP clients here are expected to be desktop/agent processes (e.g., Claude Desktop, another server-side agent), not browser JavaScript — there is no product reason to allow arbitrary browser origins to call this endpoint. If a specific trusted browser-based client ever needs access, add its exact origin explicitly; never `*`.
- **Rate limiting:** not designed in this pass — flagged as an open question (S13, Risk 3). The existing RBAC/tenant checks bound the blast radius of abuse from an authenticated user to their own church's read-only data, which lowers the urgency, but a runaway or compromised client could still generate load or excessive audit-log volume.
- **Error handling:** MCP-level protocol errors (malformed JSON-RPC, unknown method) return a JSON-RPC error object. Tool-level errors (auth denial, validation failure, RPC failure) return the _result_ of `SecureAiToolExecutor.executeTool()` translated into an MCP tool-call error content block — the existing `{success, status, code, error, denial_reason}` shape already carries everything needed; no new error taxonomy required.

## 3. Authentication model

- The human user authenticates to Grace Ledger exactly as they do today (magic link, then PIN) — MCP does not introduce a new login flow.
- An MCP client must present a valid Supabase access token (JWT) as a Bearer token on every request. Supabase's gateway rejects anything else before function code runs.
- **Staged decision (updated — see S13, Risk 2):** Supabase access tokens are short-lived (typically ~1 hour) and require a refresh-token exchange to renew. There is no bespoke "personal access token" feature in this app, and there should not be one built from scratch — a generic project-wide API key cannot carry per-user identity (Supabase's own Edge Function auth documentation is explicit that non-JWT API keys cannot be verified as a JWT by function code), which would break the RLS/RBAC model `SecureAiToolExecutor` depends on for every tool.
  - **v1 (this phase, no new infrastructure):** accept the friction. MCP is scoped to a small, trusted pilot of users who supply their current Supabase session JWT to their MCP client and re-supply it manually when it expires (~1 hour).
  - **Target state, required before MCP is exposed beyond that pilot:** enable `supabase/config.toml`'s existing `[auth.oauth_server]` block (currently `enabled = false`, `allow_dynamic_registration = false`) rather than inventing a new credential mechanism. This is a first-party Supabase Auth capability **already present in this exact project's config**, not a new build — it gives per-client revocation (revoke just the MCP connection without signing the user out of the main app), scope negotiation (e.g. a read-only-financial-data scope, an extra layer above RBAC), and clearer audit attribution than a self-reported client name. It also matches the MCP specification's own recommended OAuth 2.1 flow for remote HTTP servers — the same pattern Supabase's own hosted remote MCP server (`mcp.supabase.com/mcp`) already runs in production.
  - This document still does not implement either path — v1 requires no new code at all (it is the JWT-forwarding behavior already described above); enabling the OAuth server is a Supabase project configuration change plus its own security review, out of scope for this design pass.

## 4. Authorization model

No new authorization system. Every MCP tool call is dispatched through the existing `SecureAiToolExecutor.executeTool()`, which already enforces, per tool: `tool.requiredPermissions` via `rbac.can(role, action, resource)`, `tool.allowedRoles`, and the extra `SENSITIVE_FINANCIAL` gate. The two genuinely new tools proposed below (S6) get their own `requiredPermissions`/`allowedRoles` entries following the same table already in `src/lib/rbac.ts` — no changes to the RBAC model itself are needed, only new entries consistent with its existing shape.

## 5. Tenant isolation model

Unchanged from the existing, audited pattern (audit S7.3, steps 3-6): identity and `church_id` are **always** re-derived server-side from the authenticated JWT via a `profiles` lookup; a client-supplied `church_id` (whether from an MCP tool argument or anywhere else) is never trusted and is overwritten with the server-verified value before validation. The one existing exception — `super_admin` may specify a different `church_id` — carries over unchanged. **No MCP-specific tenant logic is introduced**; this is precisely why routing MCP through the existing executor instead of a parallel implementation matters.

## 6. MCP tool catalog

Naming note: 4 of the 6 requested tool names differ from the existing internal registry names. Recommendation: keep the internal registry names as-is (renaming them would touch the in-app Grace AI drawer and the Hermes adapter, both of which reference tools by name today — unnecessary blast radius) and have the MCP layer maintain a small external-name -> internal-name lookup for those four. The two new tools can use the same name internally and externally, since no collision exists.

| MCP-facing name            | Internal registry tool             | New code required?                                                    |
| -------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| `get_dashboard_summary`    | `get_financial_summary` (existing) | No - name mapping only                                                |
| `get_transactions`         | `get_transactions` (existing)      | Optional: pagination extension (see 6.2)                              |
| `get_funds`                | `get_fund_balance` (existing)      | No - name mapping only                                                |
| `get_budget_status`        | `get_budget_vs_actual` (existing)  | No - name mapping only                                                |
| `get_financial_report`     | **new** `get_financial_report`     | Yes - new registry entry + handler wrapping existing `ReportsService` |
| `search_financial_records` | **new** `search_financial_records` | Yes - new registry entry + handler; **no new migration** (see 6.6)    |

### 6.1 `get_dashboard_summary` -> existing `get_financial_summary`

- **Purpose:** single-call financial snapshot for a dashboard-style consumer.
- **Underlying logic:** `SecureAiToolExecutor.handleReadTool("get_financial_summary", ...)` - unchanged; queries `funds` (active, church-scoped) for total balance, and `transactions` (posted, in-period) for income/expense.
- **Input schema (existing, reused as-is):**
  ```typescript
  z.object({
    church_id: z.string().uuid(), // server-overwritten regardless of client value
    period: z.string().regex(/^\d{4}-\d{2}$/),
  });
  ```
- **Output schema (existing, reused as-is):** `{ total_income, total_expense, net_cashflow, total_funds_balance, period }` (all money fields as decimal strings, per `Money.toFixed(2)` - never raw floats).
- **Authorization:** `read` on `reports`; roles `super_admin, pastor, treasurer, finance_staff, approver`.
- **Tenant isolation:** standard (S5).
- **Pagination/filtering/sorting:** not applicable - single aggregate result.
- **Date range handling:** whole calendar month only (`YYYY-MM`), matching existing behavior; no arbitrary date range support today.
- **Error behavior:** unchanged - `TOOL_NOT_FOUND` / `UNAUTHENTICATED` / `MEMBERSHIP_NOT_FOUND` / `TENANT_MISMATCH` / `INVALID_INPUT_SCHEMA` / `PERMISSION_DENIED` / `INVALID_OUTPUT_SCHEMA` / `EXECUTION_EXCEPTION`, same codes as every other tool.
- **Audit:** same `logAudit()` call, `action: "AI_READ_FINANCIAL_SUMMARY"`, `category: "mcp_governance"` for MCP-originated calls (see S8) vs. `"ai_governance"` for in-app calls - same table, distinguishing tag.
- **Open product question (not a technical gap):** should the MCP-facing dashboard summary be enriched beyond what `get_financial_summary` returns today (e.g., pending-approvals count)? Recommend shipping the exact existing shape first; enrichment is a separate, explicitly-scoped follow-up, not bundled into this server's first version.

### 6.2 `get_transactions` (existing, name matches exactly)

- **Purpose / underlying logic:** unchanged - filtered `transactions` query by `status`/date range/`limit`.
- **Input schema (existing):** `church_id`, optional `status` enum, optional `start_date`/`end_date` (`YYYY-MM-DD`), optional `limit` (max 100, default 20).
- **Output schema (existing):** `{ transactions: any[], total_count: number }`. Note: `transactions: z.array(z.any())` is a loose output type today - flagged as a pre-existing schema-hardening opportunity (not a blocker; not this document's place to silently tighten someone else's shipped schema).
- **Gap - pagination:** the existing handler has **no offset/cursor**, only a hard `limit`. A caller cannot page past the first `limit` rows. **Recommended extension** (small, additive change to `handleReadTool`'s `get_transactions` branch and its input schema): add optional `offset: z.number().int().nonnegative().optional()` (or a cursor keyed on `transaction_date`/`id` for stable pagination under concurrent writes). This touches an existing production file (`secure-tool-executor.ts`) and is called out here for explicit approval rather than silently bundled in.
- **Sorting:** existing behavior is fixed `order("transaction_date", { ascending: false })` - no caller-controlled sort today. Recommend leaving fixed for v1 (financial transaction lists are conventionally newest-first); revisit only if a real need surfaces.
- **Filtering:** status + date range, as today.
- **Authorization / tenant isolation / audit / errors:** unchanged, same as S6.1's pattern with `action: "read"` on `transactions`.

### 6.3 `get_funds` -> existing `get_fund_balance`

- **Purpose / underlying logic:** unchanged - active `funds` for the church, optionally filtered to one `fund_id`.
- **Input/output schemas:** existing, reused as-is (`funds: [{fund_id, name, balance, target_amount}]`).
- **Pagination:** not applicable - church fund counts are small; full list every time, as today.
- **Authorization:** broadest existing role set (`member` included, read-only balances). Tenant isolation/audit/errors: standard.

### 6.4 `get_budget_status` -> existing `get_budget_vs_actual`

- **Purpose / underlying logic:** unchanged - `budgets` rows for the church/year.
- **Input schema (existing):** `church_id`, `year` (2000-2100).
- **Output schema (existing):** `{ year, items: any[] }` - same loose-typing note as S6.2's `transactions` array; flagged, not fixed here.
- **Filtering:** by year only, as today (no per-fund or per-category filter yet - real gap if finer-grained budget queries are wanted later; not addressed in this pass).
- **Authorization:** `super_admin, pastor, treasurer, finance_staff`. Tenant isolation/audit/errors: standard.

### 6.5 `get_financial_report` - new tool, reuses existing `ReportsService`

- **Purpose:** a structured, exportable financial report - the capability the brief asked for that has no existing AI-tool entry point, but **does** have existing business logic to wrap: `src/lib/reports/reports-service.ts` already exports a `ReportsService` class with `getExecutiveFinancialSummary()`, `getStatementOfFinancialPosition()`, and `getFundBalancesSummary()`.
- **No new RPC or migration needed** - this tool is purely a new registry entry + a `handleReadTool` branch that calls the existing `ReportsService` methods (constructed the same way pages already construct it: with the request-scoped `SupabaseClient`).
- **Proposed input schema:**
  ```typescript
  z.object({
    church_id: z.string().uuid(),
    report_type: z.enum([
      "executive_summary", // -> ReportsService.getExecutiveFinancialSummary()
      "statement_of_financial_position", // -> ReportsService.getStatementOfFinancialPosition()
      "fund_balances", // -> ReportsService.getFundBalancesSummary()
    ]),
    period: z
      .string()
      .regex(/^\d{4}-\d{2}$/)
      .optional(), // required for period-scoped report types
    year: z.number().int().min(2000).max(2100).optional(), // required for year-scoped report types
  });
  ```
  Exact required/optional combination per `report_type` to be finalized against each `ReportsService` method's actual parameter list at implementation time - not fully specified here to avoid guessing signatures not fully inspected in this pass.
- **Proposed output schema:** a discriminated union keyed on `report_type`, each branch matching the corresponding existing `ReportsService` return interface (`ExecutiveSummary`, `StatementOfFinancialPosition`, `FundBalanceReportItem[]`) - these interfaces already exist and are exported; the MCP output schema should be a Zod mirror of them, not a new shape.
- **Authorization:** `read` on `reports`, roles matching S6.1 (`super_admin, pastor, treasurer, finance_staff, approver`) unless a specific report type warrants tighter scoping (e.g., statement of financial position might reasonably be treasurer/pastor/super_admin only - a product decision to confirm at implementation time).
- **Audit:** new `auditAction: "AI_READ_FINANCIAL_REPORT"`.
- **Error/tenant isolation:** standard.

### 6.6 `search_financial_records` - new tool, **no schema/migration change required for v1**

- **Purpose:** free-text search over financial records - the other capability the brief asked for with no existing entry point.
- **Key finding:** the existing `get_transactions` tool already demonstrates that reads happen via plain `supabase-js` query-builder calls (`.eq()`, `.gte()`, `.lte()`, `.limit()`), not exclusively RPCs. A **v1 keyword search** can use the same pattern - a `.ilike("description", '%term%')` (or `.or()` across a couple of text columns) filter on the existing `transactions` table, scoped by the existing RLS policy exactly like every other read tool. **This needs zero new database migration.**
- **v2 (explicitly out of scope, noted for Phase 3 only):** true semantic search would require `pgvector` + embeddings - that is RAG, not this phase, and is not designed here.
- **Proposed input schema:**
  ```typescript
  z.object({
    church_id: z.string().uuid(),
    query: z.string().trim().min(2).max(200),
    start_date: z
      .string()
      .regex(/^\d{4}-\d{2}-\d{2}$/)
      .optional(),
    end_date: z
      .string()
      .regex(/^\d{4}-\d{2}-\d{2}$/)
      .optional(),
    limit: z.number().int().positive().max(50).optional().default(20),
  });
  ```
- **Proposed output schema:** `{ results: Array<{ id, description, amount, status, transaction_date, direction }>, total_count: number }` - same field shape as `get_transactions`' output, since it is the same underlying table.
- **Security requirement - explicit, not optional:** search must **never** include `member_giving`/`SENSITIVE_FINANCIAL` data by default. Scope the v1 implementation strictly to the `transactions` table (already `FINANCIAL`, not `SENSITIVE_FINANCIAL`); do not join or search member-giving records under this tool. If member-giving search is ever wanted, it must go through the same reason-required, restricted-role pattern `get_member_giving_history` already uses - a separate, explicit future tool, not a flag on this one.
- **Authorization:** `read` on `transactions`, same role set as `get_transactions`.
- **Performance note (deferred, optional):** an unindexed `ilike` scan is fine at this app's per-church data volume; a `pg_trgm` extension + trigram index on `transactions.description` would be a reasonable future optimization if search volume or table size grows - flagged as an optional, separately-approvable migration, not a v1 requirement.
- **Audit:** new `auditAction: "AI_SEARCH_FINANCIAL_RECORDS"`.

## 7. Zod validation - standardization note

All six tools follow the same two-layer validation already established: (1) MCP JSON-RPC envelope validation at the transport layer, (2) `tool.inputSchema.safeParse()` / `tool.outputSchema.safeParse()` inside `SecureAiToolExecutor`, unchanged. No new validation framework or pattern is introduced - the two new tools' schemas (S6.5, S6.6) are written in the same style as the nine existing ones in `tools-registry.ts`.

## 8. Audit integration

Reuse `audit_logs` and `SecureAiToolExecutor.logAudit()` exactly as today (audit S7.3, step 12) - same table, same dual-actor shape (`actor_id`, `church_id`, `action`, `metadata`). Two additions, both additive and backward-compatible:

- **New `category` value:** `"mcp_governance"` for MCP-originated calls, alongside the existing `"ai_governance"` (in-app Grace AI drawer) and implicitly `"ai_governance"` for Hermes today - this lets audit queries distinguish which surface originated a call without changing the table shape.
- **New metadata field:** `mcp_client_info` (from the MCP `initialize` handshake's `clientInfo.name`/`version`, which clients self-report) - logged for observability/debugging only, **never trusted as identity**. Identity remains exclusively the server-derived `auth.uid()` -> `profiles` lookup, exactly as today.

No new audit table, no new audit pipeline - this is the same one system extended with two backward-compatible fields.

## 9. Observability design (MCP-specific only - not the full Phase 6 platform)

Structured JSON logs (via `console.log` inside the Edge Function - Supabase captures these into its dashboard/`supabase functions logs`, since no logging framework exists yet per the audit):

- Incoming request: `{ event: "mcp_request", tool_name, correlation_id, mcp_client_info, timestamp }`
- Execution latency: `{ event: "mcp_tool_latency", tool_name, duration_ms, correlation_id }`
- Auth/authorization failures: `{ event: "mcp_auth_failure", code, correlation_id }` (no sensitive data - reuses the same `code` values `SecureAiToolExecutor` already returns)
- Tool/RPC errors: `{ event: "mcp_tool_error", tool_name, code, correlation_id }`
- Rate-limit events: deferred until rate limiting itself is decided (S13, Risk 3)

Sentry integration is explicitly **not** designed here (out of scope per direction) - when Phase 6 is approved, these same structured events are the natural input to a Sentry breadcrumb/event pipeline; no rework of this logging shape should be needed at that point.

## 12. Database/RPC dependencies and gaps

- **Zero new migrations required for the six tools to function.** Confirmed by tracing each tool to existing tables/services: `funds`, `transactions`, `budgets`, `audit_logs` (all already RLS-protected), plus the existing `ReportsService` for `get_financial_report`, plus a plain filtered query (no RPC) for `search_financial_records` v1.

## 13. Risks and unresolved questions

1. **MCP SDK / Deno compatibility — spiked and functionally confirmed at the code level; real Deno execution still not run (updated after the spike).** A throwaway Node.js spike (outside this repo, in a scratch directory — nothing committed) installed the real `@modelcontextprotocol/sdk@1.30.0`, imported `McpServer` and `WebStandardStreamableHTTPServerTransport`, registered one Zod-schema tool matching the shape proposed in §6, and executed real `initialize` → `tools/list` → `tools/call` requests end-to-end using only standard `Request`/`Response` objects. All three returned correct 200 responses with the expected JSON-RPC payloads. Static inspection of the two source files that matter (`webStandardStreamableHttp.js`, `mcp.js`) confirmed **zero** imports of `express`, `cross-spawn`, `cors`, or any `node:`-prefixed module, and zero use of `Buffer`/`process`/`require` — the heavier Node-only dependencies in the SDK's `package.json` belong exclusively to the separate Express-based transport wrapper, which this design does not use. Combined with Supabase's own official guide, worked example, and production hosted MCP server on the same transport class, this is now strong evidence, not a hypothesis. **What remains genuinely untested:** (a) execution under the actual Deno runtime — Deno itself is not installed on this machine, so the spike ran under Node, not Deno, and (b) a newly-identified question this spike surfaced: whether a Supabase Edge Function (which lives under `supabase/functions/<name>/`) can import a TypeScript module from outside that directory — specifically `src/lib/ai/secure-tool-executor.ts`, which this whole design's §0 architecture rule depends on reusing directly rather than duplicating. That import-path question is independent of SDK/Deno compatibility and must be checked before implementation, not assumed. Concrete, incidental finding from the spike worth keeping: in stateless mode (`sessionIdGenerator: undefined`, as recommended in §2), the SDK **requires** a fresh `McpServer` + transport pair to be constructed per request — reusing one across requests throws `"Stateless transport cannot be reused across requests"` — which conveniently matches the Edge Function per-invocation model exactly, but must be the pattern the implementation follows. If the official SDK still proves too heavy in real Deno execution, **`mcp-lite`** — a lighter library with its own Supabase-documented edge-function example — remains the recommended fallback; hand-rolling the JSON-RPC surface from scratch is a last resort.
2. **External-client credential — staged, not fully solved here (updated, see §3).** Supabase JWTs are short-lived, and a generic API key would not work regardless of lifetime since it cannot carry per-user identity for RLS/RBAC (confirmed against Supabase's own Edge Function auth documentation). **v1 accepts short-session friction** (manual JWT refresh, small trusted pilot only, no new code). **Before MCP is exposed beyond that pilot, enable the `[auth.oauth_server]` block already present but disabled in `supabase/config.toml`** — a first-party capability, not a new invention — rather than building a bespoke PAT feature. Condition to revisit: if the pilot stays small and its users accept manual refresh indefinitely, enabling OAuth may not be worth the added operational surface (consent UI, client registration management) — an operational trade-off to make deliberately once the OAuth path is confirmed as the documented target, not a security gap in the interim.
3. **Rate limiting is undecided.** RBAC/tenant scoping bounds the damage of misuse to one church's own read-only data, which lowers urgency, but doesn't eliminate the case for it (log volume, cost, abuse from a compromised credential). Flagged for a decision, not designed here.
4. **Two existing tools have loosely-typed outputs** (`get_transactions`' `transactions: z.any()`, `get_budget_vs_actual`'s `items: z.any()`) inherited as-is from the current registry - noted, not silently fixed, since tightening them is a change to already-shipped, already-tested production code outside this task's scope.
5. **`get_financial_report`'s exact input schema per `report_type`** needs to be finalized against each `ReportsService` method's real parameter list (not fully inspected in this pass) before implementation - the shape in S6.5 is a proposal, not a final contract.
6. **CI currently has zero edge-function testing/deployment steps** - adding the first one is new CI surface regardless of which tool is chosen, and should be reviewed on its own merits (deploy secrets, `supabase` CLI in CI, etc.) before implementation begins.
7. **Cross-directory import path — real constraint, with a known official workaround (updated after research).** This design's core rule (§0) depends on the MCP Edge Function importing `src/lib/ai/secure-tool-executor.ts` and `src/lib/ai/tools-registry.ts` directly, rather than duplicating their logic — but those files live outside `supabase/`, and Supabase's traditional Docker-based bundler (`supabase functions deploy`) is documented (via multiple `supabase/cli` GitHub issues) to **fail** when an Edge Function imports anything outside the `supabase/` directory tree. This is a real constraint, not a hypothetical one. **However**, Supabase now ships an experimental deploy path, `supabase functions deploy --use-api` (no Docker required for deployment), explicitly documented as solving this exact case — sharing code between a frontend and Edge Functions in the same repo. Two caveats keep this from being fully resolved: (a) it is a beta/experimental CLI flag, not yet the default, so it carries its own stability risk to track; (b) **local development and testing of the function still requires Docker** even when this flag is used for deployment — and this machine has no Docker installed either (compounding the Deno gap from Risk 1). If `--use-api` proves unreliable at implementation time, the documented fallback is a "build & sync" step (transpile the shared `src/lib/ai/*` modules to plain ESM and copy them into `supabase/functions/_shared/` as part of the deploy pipeline) — this must be an automated, single-source-of-truth sync step, never a hand-maintained duplicate, per this repo's own "Single source of truth" rule. Needs a small implementation-time check (try `--use-api` against this repo's actual layout) before committing to the approach; not a reason to abandon the "call the existing executor, don't duplicate it" architecture in §0.
