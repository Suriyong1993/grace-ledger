# Fund balance mutation is RPC-based, not trigger-based

`funds.current_balance` is mutated by inline `UPDATE funds` statements inside `SECURITY DEFINER` RPCs — `post_transaction` (`supabase/migrations/20260817000005_transaction_core_and_approval_workflow.sql:338-346,355-363`), `transfer_funds` (`supabase/migrations/20260828121608_transfer_funds_lock_order_and_grants.sql:132-134`), the void/reversal path (`supabase/migrations/20260818000006_governance_semantics_and_terminal_rejection.sql:289-309`), and `execute_confirmed_financial_action` (`supabase/migrations/20260822000016_execute_confirmed_financial_action.sql:159-263`) — rather than by a `CREATE TRIGGER` on `transactions`/`transaction_splits`; the only triggers present (`trg_validate_transaction_status`, `trg_audit_*`, `supabase/migrations/20260817000003_financial_rpcs_and_triggers.sql:275,321-346`) validate and audit, they never touch `current_balance`. This was a deliberate trade-off, not an oversight: keeping the mutation inline lets each RPC gate it behind a split-sum integrity check before touching balances (`20260817000005...sql:316-322`) and, critically, control lock acquisition order explicitly — migration `20260828121608_transfer_funds_lock_order_and_grants.sql:8-15` documents a real deadlock caused by `transfer_funds` locking funds in parameter order, fixed by locking in ascending-UUID order, a fix that is only expressible because the mutation is explicit imperative code in the RPC rather than implicit trigger-fired logic. Rejected alternative: a trigger on `transactions`/`transaction_splits` status change to "keep balance in sync" automatically — simpler to reason about in isolation, but would fire per-row across multiple `UPDATE funds` calls per RPC, obscuring the deliberate lock ordering and making the split-sum gate harder to enforce atomically with the mutation; migrating to that model now would require touching every financial RPC (`transfer_funds`, `post_transaction`, void/reversal, `execute_confirmed_financial_action`, offering RPCs).
