# Banker's rounding (ROUND_HALF_EVEN) for Money

Every `Money` value is quantized to 2 decimal places in the constructor via `val.toDecimalPlaces(2, Decimal.ROUND_HALF_EVEN)` (`src/lib/money.ts:24`) — decimal.js's own default global rounding mode is `ROUND_HALF_UP` (mode 4), so this is an explicit override away from the library default and the everyday convention, not an accident of configuration. Because `Money`'s constructor is the single choke point every monetary value in the app passes through (construction, `add`, `subtract`, `multiply`, `divide` all funnel back into `new Money(...)`), the choice is effectively permanent: switching modes later would silently change the rounding outcome of any future computation that lands on an exact half-cent boundary, without a way to distinguish old postings from new ones. Half-even is the standard choice for financial systems because repeated half-up rounding across many transactions introduces a small systematic upward bias, while half-even cancels out over a large population of roundings. Note that satang-remainder distribution for splits (`SplitEngine.distributeEvenly`/`distributeByPercentages` in `src/lib/transactions/split-engine.ts:136-201`) deliberately bypasses this rounding mode altogether, operating on integer satang with explicit first-N/last-gets-remainder rules so split sums always match the transaction total exactly — `Money`'s rounding mode only matters for future `multiply`/`divide` paths (currently unexercised by real business logic, which is a gap worth closing with an explicit rounding regression test).
